Spec 008 · Milestone D · Discovery

Search and filtering, cut down to what the brief asks

The brief asks for a search endpoint with four filters plus instruction-text search, and a UI that lets a person use them. Nothing in it asks for chips, tokens, an Apply button or a result count. This page records what gets built, what is deleted, what moved to the backlog, and the prototype decisions.

Decisions

  1. The quick filter chips are deleted. QuickFilterBar, QuickFilterBarViewModel, FilterChipView and QuickFilterBarViewModelTests are not in the brief and duplicate two of the sheet's controls. The backlog entry "Quick filter chips" points at the last commit that changed them (59650c7); when the deleting commit exists, add its hash to that entry. The README's code organization paragraph mentions the chips folder and is fixed in the same change.
  2. Native search tokens are not built. The research (verified against Apple's docs) is in the backlog as "Native search tokens and suggestions".
  3. One entry point for filters: the toolbar button. It opens FiltersSheetView, which replaces its placeholder. The button already exists (spec 005). Whether its icon changes when filters are active is a small judgment call for /spec, inside "logical, intuitive UX".
  4. The search field searches instruction text only (S6). The brief asks for no title or description search (backlog: "Search by title / description"). The prompt reads "Search instructions" so the scope is visible. Known limitation for the README: typing a recipe's name finds nothing unless its steps say it.
  5. The Filters sheet applies live. No Apply button and no result count (backlog: "Apply button and result count"). A Done button dismisses it. One small Reset control is kept as part of intuitive UX; /spec may cut it.
  6. Servings is an exact count. Backlog: "Servings ranges". Assumption to document: the brief says only "servings filter". The control only offers valid values (1 or more) and an "Any" state.
  7. Include and exclude ingredients are free-text terms (backlog: "Ingredient picker"). Matching rule to settle in /spec: case- and diacritic-insensitive "contains" on the ingredient name. Ingredient.id's doc comment in RecipeDetails.swift says the filters match on the id; that comment is updated to whatever /spec decides, since people type names, not ids.
  8. The search data is a new bundled fixture. The list JSON has no ingredients or instructions, and only 3 of 9 recipes have a details file (one deliberately malformed for E2). A new fixture holds the full record of all 9 recipes (the list fields plus ingredients and instruction text), read only by the fake server's search. The details contract and E2's failure demo are not touched. Cost: some fixture data is duplicated for the 2 well-formed details files; add a test that the shared fields agree so they cannot drift.
  9. The fake server filters. LocalRecipeAPIClient today serves <last path component>.json and cannot filter. It gains a search handler that reads the query items from the URL (RecipeEndpoint.search, built with URLComponents, as spec 002 anticipated), filters the fixture and returns list-shaped JSON. The services, DTO mapper and domain types then work as they would against a real server (D3).
  10. E1 scope. Spec 008 builds the no-results state only, and uses the system ContentUnavailableView.search as is (see Prototype below). The Library's error state is not part of this spec: it stays an E1 item with no spec yet (milestone C). Loading and empty-collection states are backlog ("Loading and empty-collection states"). The Details screen's states stay milestone E.

Where the filtering runs

The list data has no ingredients or instructions, and only 3 of 9 recipes have a details file. So the fake server needs a fuller dataset to answer S4 to S6 truthfully. A new bundled fixture holds all 9 recipes in full, read only by search. The details contract and the intentional E2 failure stay untouched.

Library view model→ Search service→ RecipeEndpoint.search (query items)→ Local fake server→ Full recipe fixture⇢ list-shaped JSON → DTO → domain → view model

The services, mapper and domain types behave as they would against a real server, so a network client can replace the fake one.

Cost: shared fields are duplicated for the two well-formed details files. A test will assert they agree so they cannot drift.

Edge cases to decide and document (E3)

These are the answers to propose in /spec. Each goes into implementation-notes.md and then the README.

CaseProposed decision
Blank or whitespace-only text, empty ingredient termDropped when the query is built, in one place. A blank query field means no filter.
Same ingredient included and excludedThe sheet prevents it (adding a term to one list removes it from the other). The endpoint treats it as logically unsatisfiable and returns an empty result, so no new error type is needed.
Vegetarian toggle offNo filter. It does not mean "non-vegetarian only".
Recipe with unknown ingredient dataWith the new fixture every recipe has data. The contract: a recipe missing the data fails an include filter and passes an exclude filter. Document it.
Out-of-range servingsThe control only offers 1 or more; the endpoint treats a value below 1 as matching nothing.
Several include termsA recipe must match all of them (AND). Exclude: a recipe is dropped if it matches any.
Malformed fixture or a thrown errorRecipeError as today, held in the existing .error view state. The screen has no error view until the error-state spec, a known gap for the README.
Overlapping searches (typing quickly)The view model keeps one search task, cancels the previous one, and does not present a cancelled result as an error. The local server answers instantly, so no debounce; the README notes a network client would debounce. This is the part of the backlog's "Cancellation handling" that spec 008 needs; the URLSession mapping stays backlog.

Open questions for /spec

Retire /recipe-list?

S1 says search with no filters returns everything, so the Library could load through search with an empty query and the list endpoint and loadRecipes() become redundant. Keeping both means two paths to the same data; retiring means changing spec 002's tests. Recommended: the Library loads through search; decide whether to delete the old path.

Settled in SPEC.md: retired.

Where the filter state lives

The Library view model and the sheet edit one query. Options: the sheet gets a small view model that the Library view model owns, or the Library view model exposes the editable query. Views get the router by initializer and never @Environment, so the sheet's dependencies are wired in RootView.

Settled in SPEC.md: a small FiltersViewModel owned by the Library view model.

Service shape

Extend RecipeListService with search(query:) or add a separate RecipeSearchService. The query type (RecipeSearchQuery, in the domain) is not in dispute.

Settled in SPEC.md: RecipeSearchService replaces the list service.

Prototype

No divergent directions: the approach was settled in this discovery, so the prototype step extracted and adapted the spec 003 frames instead (the same way specs 004 and 006 did). Read-only design snapshot: specs/008-search-filtering/design.html. It is regenerated by hand from the 003 design and goes stale if that design is edited afterward. There is no new canvas.

Seven frames: Library loaded, text search results, filtered, no results (search text), no results (filters only), Filters sheet default and with choices on.

What changed from the 003 design, and why

  • No chip row. One Filters button in the toolbar. When filters are active it turns to a filled, tinted style and its accessibility label carries the count ("Filters, 2 active"). Text search alone does not make it active.
  • Search field prompt is "Search instructions". It is S6.
  • No-results is the system view, used as is. ContentUnavailableView.search (iOS 17 and later; Apple's docs: it "conveys a search state" and "is expected to be contained within a searchable view hierarchy", so it reads the query from the field). Its symbol, title, description and wording are the system's. No custom view, no Clear Filters button: the filters are cleared with Reset in the sheet. Consequence for the build: today .searchable is attached to the loaded grid inside an if; the no-results overlay must sit inside the same searchable hierarchy.
  • The sheet: Reset on the left, Done on the right, no Apply button (changes apply live). Groups: Vegetarian only, Servings, Include ingredients, Exclude ingredients. The "Instructions" group is gone because the search field does it. Include and exclude are a text field plus removable term chips. Adding a term to one list removes it from the other.

Decisions still open after the prototype, for /spec

  • Servings control. Drawn as a menu Picker row ("Exactly", values Any and a number). Its upper bound is arbitrary (the fixture holds 2 to 6). Options: a fixed range such as 1 to 8, or values supplied by the search data. Document it as an assumption either way. Settled in SPEC.md: Any plus 1 to 8.
  • Wording for filters-only no results. With an empty search field the system view reads "No Results" with "Check the spelling or try a new search." The description is slightly off when filters are the cause. Frame 5 shows this from memory of the system text; confirm on the simulator when building. If it reads badly, the fallback is the generic ContentUnavailableView initializer with a filters-specific description, which is the first thing the "use the system view" rule would give up. Settled in SPEC.md: use the system view as is, check it on the simulator and record the wording.
  • The error state (decision 10) is not in this spec, so the Library has no error view when a search throws. It is built later with the Details error state in one shared pass under milestone E, using the View+StateOverlay extension.
